# Stage 7D-A controlled repair contract

Status: contract and acceptance design only

Baseline: Stage 7C merged `main` at `99dd1e6d3c1b8c31bb617e8322c170b87b88673b`

Stage 7D proves that `_devctl` can supervise one bounded AI-assisted repair
without giving the worker control of verification. This document defines the
boundary before repair orchestration code is implemented.

## Authority boundary

The lifecycle is:

```text
_devctl verify
      |
      +-- PASS or WARN --> record evidence and stop
      |
      +-- ERROR ---------> record error and stop
      |
      +-- FAIL ----------> create one bounded repair task
                              |
                              v
                         worker proposal
                              |
                              v
                         human approval
                              |
                              v
                    exact approved change is applied
                              |
                              v
                         _devctl verify
                              |
                         record and stop
```

The worker may propose a source change. It does not choose commands, checks,
thresholds, environments, policy, retries, status, exit codes, or the
verification implementation. `_devctl` remains responsible for every
verification decision.

The first slice permits exactly one repair attempt. There is no automatic
commit, push, merge, retry, or repair loop.

## Repair task packet

Only a deterministic `FAIL` may create a repair task. The packet is versioned
and bounded. It contains:

- `task_id`;
- `project_id` and canonical project path metadata, without allowing a path override;
- the failed verification `run_id`;
- failed check IDs, statuses, bounded summaries, bounded findings, and evidence paths;
- the allowed production-source path set;
- the forbidden path classes;
- the maximum attempt count, which is `1`;
- `_devctl` and policy provenance.

It does not contain raw process output, arbitrary commands, shell text,
environment overrides, threshold controls, or instructions generated by the
worker. Complete evidence remains in the project evidence directory.

## Pre-repair state

Before a proposal is accepted, `_devctl` records a pre-repair snapshot:

- project identity and canonical root;
- `HEAD` commit and branch name;
- clean index and clean worktree state;
- canonical index state/hash;
- tracked and untracked file paths;
- SHA-256 hash, size, and file type for every relevant file;
- the baseline failure task ID and verification run ID.

If the pre-repair index or worktree is dirty, repair orchestration is rejected.
That dirty state is recorded as evidence. Preserving pre-existing changes is
deferred until a later stage.

## Proposal and exact approval

The worker returns a bounded proposal containing an exact patch, not a command
to generate a patch. `_devctl` stores the canonical patch bytes as an immutable
proposal artifact and calculates:

```text
diff_hash = SHA-256(exact canonical patch byte sequence)
```

The canonical patch artifact is UTF-8, uses LF (`\n`) line endings, uses
canonical project-relative paths with `/` separators, and contains no
timestamps or implementation-specific metadata. Binary patches, mode changes,
renames, additions, and deletions are rejected in this first slice. The hash
is calculated over the stored bytes, and application uses those same immutable
bytes; `_devctl` never regenerates the patch from worker fields after approval.

Before modification, the visible approval screen shows:

- project and task IDs;
- failed check and source evidence;
- exact file paths in the patch;
- additions, modifications, and deletions;
- the complete bounded diff;
- `diff_hash`;
- worker identity and protocol version.

Approval binds to that exact hash. Approving a task without approving its
specific diff is not valid. A changed proposal requires a new validation and a
new approval.

The first slice permits modifications to existing production-source files in
the trusted allowlist only. New files and deletions are rejected in this
slice. A later contract may extend this after separate review.

## Trusted and forbidden paths

Paths are canonical, project-relative paths. Symlinks and path traversal that
escape the project root are rejected.

The worker may modify only explicitly allowed production-source paths from
trusted, versioned configuration. The worker cannot add paths to that allowlist.

The following are always forbidden:

- tests and test fixtures;
- `_devctl` policy or configuration;
- project verification configuration;
- `.git` metadata;
- CI and workflow files;
- generated evidence and workflow journals;
- build outputs and dependency caches;
- scripts or commands used to bypass verification.

The source allowlist must not include any forbidden path class.

## Pre-apply validation and all-or-nothing application

Immediately before any write, `_devctl` revalidates the approved baseline:

- current `HEAD` equals the approved baseline `HEAD`;
- current branch and index state/hash equal the approved baseline;
- current worktree file paths and hashes equal the approved baseline;
- current project identity equals the approved project identity;
- current verification and policy provenance equals the approved provenance.

Any mismatch stops the workflow before modification and emits no
`PATCH_APPLIED` event.

The stored immutable patch must pass a complete applicability preflight before
writing. Application is all-or-nothing: success produces the complete patch,
and failure leaves the exact pre-apply file/index state. A mechanism that
cannot guarantee this transaction boundary is rejected before it can modify a
project. A failed restoration is an `ERROR`; verification does not run.

```text
PRE_APPLY_STATE_VALIDATED
          |
          v
PATCH_PREFLIGHT
          |
          +-- cannot apply --> STOP, original state required
          |
          v
PATCH_APPLIED atomically
```

## Apply and post-change validation

After the pre-apply checks and successful preflight, `_devctl` applies only the
immutable approved patch. It then captures a post-change snapshot and compares
the actual filesystem/Git delta with the approved proposal.

The repair is valid only when all of these match:

```text
approved diff hash
        ==
actual post-change diff hash
```

and:

- every changed path is in the approved allowlist;
- no forbidden path changed;
- no extra file was added, deleted, or modified;
- every approved file has recorded pre- and post-change hashes;
- the project identity and verification configuration are unchanged.
- the patch was applied as one all-or-nothing transaction.

Each changed file receives provenance containing its relative path, change
type, pre-hash, post-hash, byte sizes, and task ID.

## Fail-closed outcomes

The workflow records a bounded failure and stops immediately for:

- approval rejection;
- cancellation or worker interruption;
- worker protocol or worker execution error;
- malformed or oversized proposal;
- altered patch after approval;
- diff hash mismatch;
- baseline `HEAD`, index, worktree, identity, verification, or policy provenance changed before apply;
- the approved patch cannot pass complete applicability preflight;
- patch application errors or cannot prove restoration of the exact pre-apply state;
- extra file change;
- unexpected addition or deletion;
- forbidden path change;
- path traversal or symlink escape;
- inability to capture pre/post provenance;
- `_devctl` verification `ERROR`.

No automatic cleanup, second worker attempt, commit, push, merge, or status
reinterpretation is allowed after a fail-closed condition.

## Deterministic re-verification

Only after post-change validation succeeds does `_devctl` run its ordinary
verification path. The worker cannot select the commands or checks. The result
is recorded as one of:

- `PASS`: repair succeeded;
- `WARN`: repair verification completed with warnings;
- `FAIL`: the original or another deterministic failure remains;
- `ERROR`: verification infrastructure failed and the workflow stops.

The workflow always stops after this result. A `PASS` or `WARN` does not create
another attempt, and a `FAIL` does not automatically invoke the worker again.

## Evidence and event sequence

The evidence must connect the full lifecycle using one task ID and the related
verification run IDs:

```text
REPAIR_TASK_CREATED
BASELINE_CAPTURED
WORKER_PROPOSAL_RECEIVED
PROPOSAL_VALIDATED
DIFF_DISPLAYED
APPROVED or REJECTED
PRE_APPLY_STATE_VALIDATED
PATCH_PREFLIGHT
PATCH_APPLIED
POST_STATE_CAPTURED
DELTA_VALIDATED
VERIFY_STARTED
VERIFY_FINISHED
REPAIR_STOPPED
```

`PATCH_APPLIED` is emitted only after approval. `VERIFY_STARTED` is emitted
only after the actual delta matches the approved diff. Evidence contains the
bounded task/result envelopes, diff hash, approval decision, file provenance,
verification result, and references to complete durable evidence. It does not
copy raw process output into the worker packet.

## Synthetic Go acceptance scenario

Use a small isolated project:

```text
synthetic-go-repair/
  go.mod
  calculator.go
  calculator_test.go
```

The existing test deliberately exposes a production defect in
`calculator.go`, for example an `Add` implementation that subtracts instead
of adding. The baseline deterministic verification must produce `FAIL`.

The approved worker proposal changes only `calculator.go` to restore the
correct implementation. `calculator_test.go` is immutable and is not part of
the worker allowlist.

Acceptance must prove, in order:

1. baseline identity, Git state, and file hashes are captured;
2. ordinary verification returns `FAIL`;
3. one bounded repair task is created;
4. the worker returns an exact proposal;
5. `_devctl` validates the proposal and allowed path;
6. the exact diff and hash are visibly displayed;
7. a human approves that exact diff;
8. the approved change is applied;
9. actual delta and per-file hashes match the proposal;
10. `_devctl` independently re-verifies;
11. the final `PASS`, `WARN`, `FAIL`, or `ERROR` is recorded;
12. the workflow stops with no second attempt.

## Negative acceptance matrix

The first slice must also prove fail-closed behaviour for:

| Case | Expected result |
| --- | --- |
| Worker changes a test | Reject; no verification rerun |
| Worker changes policy or project config | Reject; no verification rerun |
| Worker changes an extra unapproved file | Reject; record delta mismatch |
| Worker adds or deletes a file | Reject in the first slice |
| Patch is mutated after approval | Reject diff-hash mismatch |
| Baseline changes after approval | Reject before modification |
| Approved patch cannot apply cleanly | Reject before modification |
| Patch application errors | Stop; never verify |
| Actual bytes differ despite same changed paths | Reject delta |
| HEAD/index changes during repair lifecycle | Reject |
| Policy/config provenance changes before apply | Reject |
| Worker returns an oversized or malformed proposal | Reject protocol error |
| Human rejects the exact diff | Record rejection and stop |
| Human cancels the approval | Record cancellation and stop |
| Worker exits or times out | Record worker error and stop |
| `_devctl` re-verification returns `ERROR` | Stop immediately; no retry |
| Re-verification returns `FAIL` | Record unsuccessful repair and stop |

Stage 7D-A is accepted only when the positive synthetic run and this negative
matrix are represented by durable evidence and regression tests. Implementing
the worker adapter, patch application, or repair loop belongs to the next
implementation slice after this contract is approved.
